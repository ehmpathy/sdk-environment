# 🌙 dream: check the publish npm's engine against the repo node in pr ci

- kind: reseed
- owner: ehmpathy/declapract-typescript-ehmpathy (`cicd-package` practice)
- caught 2026-11-25

## .the cue that fired

the `role-standards-coverage` review of the npm@11 fix held the clamp out of ci: `verify.publish-npm-pin` proves the pin, but only when a human runs it.

## .the gap, precisely

- the `verify oidc compat` step in `.publish-npm.yml` runs only on a release tag
- so a pr that changes the npm spec, or bumps `.nvmrc` out of the npm's engine range, passes pr ci and fails at the tag. that is how v0.1.6 of sdk-environment went red
- sdk-environment now clamps this in its own pr ci: `.agent/repo=.this/role=any/skills/verify.publish-npm-pin.integration.test.ts` runs the workflow's line on the `.nvmrc` node
- the upstream practice still has no such check, so every other adopter keeps the gap

## .the shape of the fix

- in the upstream practice, add a pr-time step (in `.test.yml`, beside `test-types`) that runs `npm install -g npm@<spec>` into a temp prefix on the `.nvmrc` node and checks `npm --version >= 11.5.1`
- read `<spec>` from `.publish-npm.yml`, as `.agent/repo=.this/role=any/skills/verify.publish-npm-pin.sh` does, so the check cannot drift from the line it guards
- across adopters, a `.nvmrc` may be loose (`22`, `22.x`) or an alias (`lts/*`). sdk-environment's skill matches exact and loose pins against the current node; an alias still needs fnm to look it up. an upstream pr-ci step sidesteps this: it runs after `setup-node`, so the runner's node already is the `.nvmrc` node
- then `declapract.upgrade` carries it to sdk-environment and every other adopter

## .why it is not done in this round

this route is a nano fix in sdk-environment. the upstream practice is another repo; its change and its rollout to every adopter is its own pr there.
