# 🌙 dream: evict stale account-name cache files

- kind: fix
- owner: sdk-environment
- caught 2026-11-16

## .the cue that fired
peer review (r010, i003) noted the shared cache never removes a file. one file lands per access key; under sso or rotated keys each process mints a new key, so files accrue in `$TMPDIR/sdk-environment.uid=$uid/aws-account-name/` until the os clears its temp dir.

## .the gap, precisely
- each file is ~50 bytes plus a `.failed` mark at most; no read cost, since a lookup opens only its own key
- no code deletes a file past its ttl
- measured 2026-11-16, one day of test runs on a grove host: `tree -pa /tmp/sdk-environment.uid=1002` → 70 files, each `-rw-------`, dir `drwx------`. the keyrack test session mints a fresh access key per unlock, so each run's key lands its own file
- that host's `/tmp` persists and never auto-cleans, so the os temp sweep cannot be relied on to reclaim them

## .the shape of the fix
on a cache write, sweep the dir best-effort: `rm` each `*.json`, `*.failed`, and orphan `*.tmp` whose mtime is older than 2× ttl, with fs faults swallowed (the same `isFsFault` boundary). bound the sweep to once per process. clamp: a dir with an old file and a fresh one; after a write, only the fresh one remains.

## .why it is not done in this round
no harm ships: 70 files a day is ~3.5 KB, owner-only, and a lookup never lists the dir, so growth costs disk alone, at a rate a host can absorb for years. a sweep adds a code path to a lock-adjacent dir that the commit window does not need. raise it if a host shows a count large enough to matter.
