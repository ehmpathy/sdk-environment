# 1.vision.experience.case=_

input axes and the nested `upgrade gate` are declared in `1.vision.experience.dimensions.md`. `feel` (happy · sharp) and `care` (critipath · alterpath) are not inputs: each is the verdict a cell earns from those axes, so the grid below sorts by them and the dimensions file does not list them.

## actors × feel

| actor | happy | sharp |
|---|---|---|
| maintainer | merges fix, then release pr v0.1.7 → sees the tag publish go green (critipath, `case=1`) | a bad pin (typo, wrong range) would pass pr ci unseen, as the publish job runs only on a tag (alterpath; fail-safe = the `verify.publish-npm-pin` clamp runs the workflow's own line on the `.nvmrc` node in every pr's ci — see the clamp walk below) |
| publish job | installs npm 11.x on node `v22.21.0`, publishes with provenance (critipath, `case=1`) | a future 11.x rejects the node → step red on `EBADENGINE`, npm prints the range it needs (alterpath, `case=2`) · the suite flakes on the tag → publish never starts, run is red, a re-run clears it (alterpath) · a prior payload clashes → `idempotify` fails loud with both shasums (alterpath) |
| consumer | `npm view` reads 0.1.7 → pins it, gets #18 (critipath, `case=1`) | pins 0.1.7 before it lands → npm `ETARGET`, names the absent version (alterpath; registry behavior, not ours) |

density: `case=1` crosses six boundaries (merge · release pr · tag · runner engine · registry oidc · consumer read) and subsumes every happy cell, so it is the centered demo. `case=2` spotlights the one sharp edge this fix touches, so its fail-safe stays legible.
