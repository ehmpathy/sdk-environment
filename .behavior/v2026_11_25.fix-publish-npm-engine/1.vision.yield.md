# 1.vision: sdk-environment publishes its release to npm

## the solution

pin the oidc npm upgrade in `.github/workflows/.publish-npm.yml` from `npm@latest` to `npm@11`.

```diff
-            echo "npm $NPM_VERSION < $MIN_VERSION, will upgrade npm now to support oidc..."
-            npm install -g npm@latest
+            echo "npm $NPM_VERSION < $MIN_VERSION, will upgrade npm to the latest 11.x for oidc..."
+            npm install -g npm@11
```

### why it works

- the runner node is `.nvmrc` = `v22.21.0`; setup-node ships npm `10.9.4` with it
- oidc trusted publish needs npm `>= 11.5.1`, so the step must upgrade
- `npm@latest` = `12.2.3` today, engine `^22.22.2 || ^24.15.0 || >=26.0.0` → `v22.21.0` fails → `EBADENGINE`
- `npm@11` = `11.21.3` today; every 11.x declares engine `^20.17.0 || >=22.9.0` → `v22.21.0` passes, and `11.21.3 >= 11.5.1` keeps oidc
- ⇒ the major pin stops a future npm major from a second break of the publish; patches within 11.x still flow
- fulcrums: `@11` over an exact pin (F01, 92% — the practice is checked by exact equality) · pin npm over a node bump (F02, 95% — a bump moves every job and leaves `latest` unpinned); both clean reworks, `.fulcrums/`

### why it conforms rather than invents

- the line is a copy of the `cicd-package` practice in `ehmpathy/declapract-typescript-ehmpathy`
- upstream already pins `npm install -g npm@11` (`src/practices/cicd-package/best-practice/.github/workflows/.publish-npm.yml:56`)
- ⇒ this repo held a stale copy; the cure matches upstream, word for word on those two lines

### how #18 reaches npm

- #18 (`2d33ccb`) shipped in release **v0.1.6** (`1b14d96`); its publish run `45077327227` went red, so npm `latest` stays `0.1.5`
- a re-run of that run cannot cure it: a tag run reads the workflow at the tag, which holds `npm@latest`
- ⇒ after this `fix(publish)` merges, the repo's `please-release` action opens release pr **v0.1.7** (default bump = patch, `.github/actions/please-release/action.yml`); its merge cuts the tag, which holds the pin and carries #18
- done = `npm view sdk-environment version` reads `0.1.7`

## the outcome world

- before: a release pr merge cuts a tag, the tag publish goes red at `verify oidc compat`, npm lags; no consumer can pin the release that holds #18
- after: the tag publish installs npm 11.x and publishes with provenance; `declapract-typescript-ehmpathy` pins `sdk-environment@0.1.7` and gets #18
- aha: the release that "shipped" #18 never left github; one word restores the pipe

## mental model

- a maintainer says: "the publish grabbed an npm too new for our node; we pinned it to npm 11"
- analogy: an unpinned `latest` dependency, the hazard `rule.require.pinned-versions` names, here inside ci

## evaluation

- pros: a two-line fix · matches upstream · no runtime or consumer change · keeps oidc + provenance
- cost: a repo skill (`verify.publish-npm-pin`) and its integration test ride with the fix, so every pr's ci runs the workflow's upgrade line on the `.nvmrc` node. it is the regression clamp the fix owes; a one-time check would catch only today's instance (fulcrum F05, clean rework: delete three files)
- cons: the publish job itself still fires only on a release tag
  - bound: the clamp runs the same line, read from the workflow, with the workflow's own skip guard; post-merge, v0.1.7's publish run is the final proof
- edgecase: npm drops node 22.21 support within 11.x → not seen across all 38 published 11.x versions; if it comes, the clamp turns the next pr red before a tag meets it (`case=2`)
