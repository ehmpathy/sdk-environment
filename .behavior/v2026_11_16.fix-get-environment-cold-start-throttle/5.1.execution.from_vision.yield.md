## found in execution
- node core errors under jest come from another realm, so `error instanceof Error` is false for fs errors. the first draft's ENOENT allowlist never matched under jest, and every in-jest call threw. the cross-process test passed (tsx, one realm) and hid it. fix at cause: match errors by shape (`code`, `name`), never `instanceof`. the in-jest suites now pin it.

- a dir name keyed by uid is not ownership: on a shared host another os account can pre-create it and plant a cache file whose name is the hash of a non-secret access key id. a cache file is trusted only when this process's os account owns it; a foreign file reads as cold. clamp: `withCacheAcrossProcesses.integration.test.ts` [case8], red with the check reverted (`Received: "acme-planted"`), green restored. the dir itself is trusted only when ours and no symlink; a loose dir of ours is closed to 0700 ([case15], [case16]).

- the cache is an optimization, so no fs fault may fail a caller whose fetch would succeed. every fs call degrades on any node system error (`code` + `syscall`), not on an errno list. clamp: [case11], red with the read reverted to ENOENT only (`EISDIR: illegal operation on a directory, read`), green restored.

- a holder that fails, and a holder that dies, must be told apart. on a failure that keeps no queue (a credential error, which would fail every waiter the same way), the holder writes a `<key>.failed` mark with the time, then releases; a waiter that sees a mark newer than its wait fetches direct, in parallel. on a throttle (`isQueueKeptOnError: isThrottleError`) or a death, no mark lands, so the next waiter takes the lock: a throttled api sees one caller at a time, and a killed holder costs one fetch, not N. clamps, each red with the waiter sent direct on any wait, green restored:
  - [case13] credential failure: 10 callers fetch in parallel, under 1500ms (`Received: 2707` when queued)
  - [case17] holder killed mid-wait: 1 fetch for 10 callers (`Received: 3`)
  - [case18] holder throttled past retries: 2 fetches for 10 callers, 1 rejected (`Received: 10`)

- which holder failures keep the queue is an allowlist: `isServerTransientError` (a throttle by name or 429, or a 5xx the sdk marks `$fault: 'server'`). those may clear for the next caller, so aws sees one caller at a time. every other failure (a credential refusal, an unreachable host) fails each caller the same way, so the waiters are freed to see it at once. clamps:
  - sharedCache [case5] a holder 5xx, 10 callers → 2 calls, 1 rejected. red with a throttle-only predicate (`Received: 10`)
  - sharedCache [case6] an unreachable host, 10 callers → 10 rejections in under 1.5s. red with a queue-on-any-non-credential predicate (`Received: 3397`)

- the key read touched `client.config.credentials`, which a downstream module-level mock of the sdk does not build, so such a suite got a `TypeError` where the old code returned the mocked tier. the seam now returns a null key when the client holds no credential provider, and the parser asks direct with no cache. clamp: `getAccessKeyIdFromAccountClient.test.ts` [case2] passes a config-less client, as such a mock builds; red before the fix (a `TypeError` on the undefined `config.credentials`), green after. no module mock is used.

- the prod modules load at import time for every caller, so they use bare core module names, `fs.promises`, a local `sleep`, and `randomBytes`; `timers/promises` (node 15+) and `randomUUID` (node 14.17+) are gone from prod. the import floor is node 14.14 (`fs.promises.rm`).

- a dead-pid lock the fs refuses to delete (a 0500 dir, a read-only remount) made a fresh caller spin: the break reported success, and the loop retried at once, forever. the break now reports `BROKEN` only once the lock is gone; a refused delete fetches direct. clamp: [case19], red before the fix (`Exceeded timeout of 90000 ms`), green after, under 1s.

- the real throttle shape was unproven. `getEnvAccessFromAwsAccountName._.realThrottle.integration.test.ts` points the real sdk at a local fake of the account api (`AWS_ENDPOINT_URL_ACCOUNT`) that replies 429 `x-amzn-errortype: TooManyRequestsException` 4 times, then the name. 8 cold callers all get `test`; the api sees 5 calls: the sdk's own 3, then this layer's retry. red with `isThrottleError` keyed on another name (`Received: 11`, callers rejected), green restored.

- the default sdk seam had no hermetic proof. [case4] sets env credentials and a cache file under their key; the real seam answers from the file. red when the seam reads the wrong field, green restored.
