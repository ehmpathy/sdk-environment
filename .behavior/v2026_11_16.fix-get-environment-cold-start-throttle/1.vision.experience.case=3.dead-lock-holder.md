# case=3 — the lock holder dies, throws, or leaves no pid

cells: l05 · l06 · l08 · l11 · l12 · l21.

## narrative
jest kills worker 7 on a timeout while it holds the lock. the lock dir stays on disk, with worker 7's pid inside. worker 12 polls (l05), or arrives five seconds later (l06). it reads the pid and asks the os whether that pid lives. it does not, so worker 12 breaks the lock at once, takes it, asks aws, and writes the file. no one waits out a timeout for a dead process.

if the holder throws instead, it stays alive and removes the lock in a `finally` (l08). what the waiters do turns on the error. a credential error would fail each of them the same way, so the holder marks the failure first and every waiter asks aws itself, at once, in parallel; none queues behind another. so does an unreachable host. a failure that may clear for the next caller (a throttle that outlasted the holder's retries, a 5xx) leaves no mark, so the next waiter takes the lock and asks aws once more; an api under strain sees one caller at a time. no wait passes the stale bound.

if the holder died and the dir has since turned read-only, worker 12 reads the dead pid but the fs refuses to delete the lock (l21). worker 12 does not retry the break in a loop; it asks aws direct, at once, and returns its tier. a refused break costs one aws call, never a hang.

if the holder is killed while N processes wait, it leaves no mark. one waiter breaks the dead lock and takes it; the rest keep their wait and read its file.

if the holder died before its pid landed (a torn write), no waiter can tell whether it lives (l11, l12). the lock breaks once it is older than the stale bound (60s). this is the one path that costs a full bound's wait; it needs a crash inside a window of a few microseconds, and it never deadlocks.

## bdd [tn]
```
given a lock whose holder pid is dead, and a cold cache
  [t0] when a process reads the account name
    then it sees the holder is dead and breaks the lock at once
  [t1] when it takes the lock
    then it asks aws once and writes the cache

given a holder whose fetch fails with a credential error while N processes wait
  [t0] when the holder's fetch throws
    then the holder marks the failure, drops the lock in `finally`, and its caller sees the error
  [t1] when the waiters poll
    then each sees the mark and asks aws itself, in parallel

given a holder throttled past its retries while N processes wait
  [t0] when the holder's fetch throws the throttle
    then the holder drops the lock with no mark, and its caller sees the error
  [t1] when the next waiter polls
    then it takes the lock and asks aws once more; the rest wait, then read its file

given a holder killed while N processes wait
  [t0] when one waiter polls
    then it sees the holder is dead, breaks the lock, takes it, and asks aws once
  [t1] when the rest poll
    then they read its file

given a lock with no readable pid
  [t0] when a process polls while the lock is younger than the stale bound
    then it keeps its wait
  [t1] when the lock passes the stale bound
    then it breaks the lock, takes it, asks aws once, and writes the cache

given a dead holder's lock in a dir the fs will not let the waiter delete from
  [t0] when a process reads the account name
    then its break is refused, and it asks aws direct at once, well inside the stale bound
    then it returns its tier
```
