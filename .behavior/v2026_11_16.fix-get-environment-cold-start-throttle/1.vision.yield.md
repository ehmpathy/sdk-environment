# 1.vision — getEnvironment survives a cold start across test processes

## .hour

the wish set 2026-11-16 1342Z. at route start the clock read 1426Z (github `Date` header). the hour is missed; the wisher was told at once. the rest of done holds and the drive continues with the smallest change.

## the outcome world

### before
a 36-core grove runs ~35 jest workers. each worker owns a cold module registry, so each one calls `GetAccountInformation`. the aws account api refuses the burst with `TooManyRequestsException`. 7–9 tests fail per run, a different set each run.

### after
the first cold process takes a lock (a dir that holds its pid) and asks aws once. it writes the account name to a file in the os temp dir, keyed by a hash of the caller's access key id. every other process waits on the lock, then reads the file. if aws still throttles that one call, it backs off with jitter and retries. the suite is green on 4 cores and on 36.

### aha
`getEnvironment()` costs one aws call per machine per ttl, not one per jest worker.

  - `case=6.untrusted-disk-is-never-believed.md` — a file another account owns, a symlinked dir, or a torn or wrong-shape file is never believed
  - `case=7.holder-outlives-its-lock.md` — a retaken lock stays with its new owner; a holder that never lets go meets the deadline

## mental model
"the sdk now asks aws for the account name once per machine, and shares the answer." analogy: one roommate checks the mailbox; the rest read the note on the fridge.

## evaluation
- pros: kills the burst at its cause; serves any multi-process caller, not jest alone; no new dependency
- cons: a file in the temp dir; a lock with a stale-break timeout
- pit of success: the key is a hash of the access key id, so no secret lands on disk, and a switch of credentials can never read another caller's name. file mode 0600, a dir per os account.

## open questions & assumptions
- [answered] what ttl? 15 min. an account rename is rare; a long suite pays one extra call per ttl.
- [answered, ruled F1] what keys the cache? a hash of the resolved access key id: no network call, and a key names only the credentials that minted it. env creds (issue #17's grove, ci) share one key across workers → one call. sso profiles mint a fresh key per process (`credential-provider-sso/dist-cjs/index.js:57-66`), so under sso there is no share; the retry is the only guard, and the readme says so. a dream holds the sso share.
- [answered] what if the temp dir is unwritable? on any fs fault, or a dir another os account owns, the shared cache is skipped and the fetch runs direct, as today.
- [answered] how long may a dead lock block? not long: the lock holds the holder's pid; a waiter that finds the pid dead (same host) breaks it at once. a 60s stale bound backs this up when the pid cannot be read.
- [answered] how patient is the retry? more than the sdk's own 3 attempts (verified 429 → sdk retry): our layer adds attempts with full jitter and an exponential cap.
- [answered] is the alias parser (`ListAccountAliases`, iam) in scope? no: done names the account api, and no iam throttle was measured. dream caught.
- [research] does iam throttle `ListAccountAliases` under the same burst? deferred to the alias dream; no measurement exists.

## groundwork

### external research
- aws account api `GetAccountInformation` — throttle surfaces as `TooManyRequestsException` (seen in the issue's stack traces)
- aws sdk v3 clients expose `client.config.credentials()` → resolves `{ accessKeyId, ... }` with no extra api call

### internal research
- `src/domain.operations/parsers/access/getEnvAccessFromAwsAccountName.ts:44-93` — the parser; try/catch allowlist returns null on credential errors
- `src/domain.operations/getEnvironment/getEnvironment.ts:106-111` — in-process cache only
- tests: `getEnvAccessFromAwsAccountName.integration.test.ts` — the invalid-credentials case must still return null (a distinct access key gives a distinct cache key, so it still does)

## what is awkward
- a file lock in a library is heavier than a module cache. it is the smallest mechanism that spans processes with no daemon.
- waiters poll; a 50–100ms poll adds at most that much latency to each cold waiter.
